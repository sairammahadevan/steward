Overview

STEWARD is a personal home document management system built on a privacy-first, local-first architecture. It ingests documents of any type, extracts structured metadata using a cloud LLM (Anthropic Claude), stores everything locally in SQLite, and surfaces time-sensitive reminders proactively via WhatsApp.

The system is designed around a swarm of specialised agents — each owning a distinct domain — following a phased MVP delivery model with explicit QA gate reviews between each phase.

Swarm Agent Architecture

STEWARD is built by a swarm of 5 specialised agents, each with clearly defined file ownership and responsibilities. No agent touches another agent's domain. This pattern enables parallel development, clear accountability, and meaningful QA gate reviews between each MVP.

🎯
Product Owner
Owns: .swarm/board/

Represents user needs. Maintains the backlog and sprint board. Makes MVP gate decisions based on QA reviews. Ruthlessly cuts scope when phases grow beyond definition.

Principle: "Would Sairam actually use this daily?"
🏛️
Architect
Owns: .swarm/architecture/ · pyproject.toml

Owns system design and cross-cutting concerns. Writes Architecture Decision Records (ADRs) to document every significant technology choice with explicit tradeoffs. Guards against over-engineering.

Principle: "Can I remove this and still solve the problem?"
⚙️
Backend Developer
Owns: src/ (non-UI)

Owns all Python logic — Claude client, document parser, metadata extractor, SQLite layer, query engine, scheduler, and alerter. Every module is independently testable with typed interfaces.

Principle: "Logging and error handling are not optional."
🎨
Frontend Developer
Owns: src/ui/

Owns the Flask UI — routes, Jinja2 templates, and CSS. Calls backend functions cleanly with no business logic in the UI layer. Responsible for loading states, error handling, and making the system feel effortless.

Principle: "If you have to think about how to use a page, it's too complicated."
🔍
QA Agent
Owns: tests/ · .swarm/reviews/

Reads everything, writes all tests, produces the gate review that determines whether an MVP can proceed. Checks every acceptance criterion. Never implements fixes — only reports issues for the relevant agent to address.

Principle: "A false PASS is worse than a FAIL."
Architecture Decision Records

Every significant technology choice is documented as an ADR — capturing the context, the decision, and the explicit tradeoffs accepted. These live in .swarm/architecture/.

ADR-001
Claude API over local LLMs
Context: Previous attempt used Ollama + Gemma 3B on an M3 8GB MacBook. The machine ran out of memory, crashed during inference, and 3B models produced unreliable extraction from legal documents and scanned images.

Decision: Use Anthropic Claude API. Haiku for ingestion (fast, cheap), Sonnet for query answering (better reasoning).

Tradeoff accepted: Document text transits Anthropic servers during API calls. Mitigated by: 7-day deletion policy, no training use, actual files stay local.
ADR-002
SQLite over vector database
Context: Previous attempt used Qdrant vector DB, requiring a separate server process, embedding pipelines, and chunking strategy decisions — all of which contributed to the project stalling.

Decision: SQLite with structured metadata cards. One row per document. Keyword matching for retrieval. Claude handles the full document in-context.

Tradeoff accepted: No semantic/fuzzy search across content. Acceptable at personal document scale (50–200 documents). Vector search can be added if collection grows.
ADR-003
Flask over Streamlit or FastAPI
Context: Streamlit's execution model caused state management issues. FastAPI + separate Streamlit frontend added operational complexity for a personal tool.

Decision: Flask with Jinja2 templates. Single process, single port, one command to run. No JavaScript build pipeline.

Tradeoff accepted: Full page reloads on form submit. No real-time updates. Acceptable for personal-use ingestion and query workflows.
ADR-004
PyMuPDF for document parsing
Context: STEWARD must handle text PDFs, scanned (image-based) PDFs, and DOCX. The parser must detect document type and route correctly — text extraction for text PDFs, image conversion for scanned pages.

Decision: PyMuPDF for PDF parsing and image rendering. python-docx for DOCX. Detection rule: <50 characters per page = treat as scanned.

Tradeoff accepted: AGPL licence (acceptable for personal use). Image conversion increases token usage for scanned documents.
MVP Delivery Model

Each MVP is gated — no code for the next phase begins until the current phase passes QA review. This prevents over-building and ensures each increment is usable on its own.

MVP 1 · Shipped
Ingest & Extract

Upload any document → Claude extracts structured metadata card → stored in SQLite → visible in UI. SHA-256 deduplication. Text and scanned PDF support.

MVP 2 · Shipped
Ask Anything

Natural language questions answered from document vault. Keyword-based retrieval from SQLite, full document context sent to Claude Sonnet, cited answers returned.

MVP 3 · Next
Proactive Alerts

APScheduler runs daily, queries SQLite for items due within configurable window, sends WhatsApp message via Twilio API. No action required from user.
