Overview

STEWARD is a privacy-first, local-first personal document intelligence system built for a single user on their own machine. It ingests documents of any type — including scanned image PDFs — extracts structured metadata using Anthropic Claude, stores everything in SQLite, and makes it queryable through a conversational interface and full-text search.

The system uses a two-model Claude strategy — Haiku for fast/cheap text extraction, Sonnet for vision (scanned docs) and multi-turn reasoning — backed by a semaphore-limited concurrent API layer with exponential backoff. Every feature is designed to feel local and instant even though heavy processing runs asynchronously in background threads.

🖥 Local-first — all files on disk, SQLite DB
🔄 Async-first — background threads, live progress
🤖 LLM-first — Claude reads the whole document
🔒 Privacy-first — files never leave the machine

Key Engineering Decisions
⚡
Async-first ingestion

Files are saved to disk and an HTTP redirect fires immediately. Background threading.Thread(daemon=True) handles all Claude API calls. The user sees live progress without waiting at a loading screen. Job state survives tab switches via Flask session.

🎛
Semaphore-limited API concurrency

threading.Semaphore(2) serialises Claude API calls. Without this, uploading 5 scanned PDFs simultaneously would send 5 large image payloads in parallel — causing consistent API timeouts. Two concurrent calls is the empirically safe limit.

🧠
Two-model extraction strategy

Haiku handles text extraction — fast and cheap for structured docs. Sonnet handles vision extraction — scanned PDFs need Sonnet's OCR reasoning. Re-ingests always use Sonnet + 150 DPI (vs 100 DPI first-pass) because quality is the explicit goal at that point.

🗄
SQLite over vector database

Previous attempt used Qdrant — separate server, embedding pipeline, chunking strategy. STEWARD uses SQLite one row per document, keyword match for retrieval, then Claude reads the full document in-context. Zero ops, no new dependency, works at personal collection scale.

🔄
Native multi-turn via messages API

Chat history stored as a proper Claude messages array [{role, content}] in Flask session. Document context lives in the system prompt. Each request passes full history to the Anthropic messages API — Claude maintains context natively without any summarisation needed.

🛡
Safe schema migrations

Every new column is added with ALTER TABLE … ADD COLUMN inside a try/except OperationalError. No migration framework, no version tracking — just idempotent statements. Existing databases upgrade silently on restart.

Architecture Decision Records
ADR-001
Claude API over local LLMs
Context: Previous attempt ran Ollama + Gemma 3B locally on an M3 8GB Mac. The machine ran out of memory mid-inference, crashed, and 3B models produced unreliable extraction from legal documents and scanned images.

Decision: Anthropic Claude API. Haiku for text ingestion (fast, cheap). Sonnet for vision and query answering (better reasoning, superior OCR).

Tradeoff accepted: Document text transits Anthropic servers. Mitigated by: 7-day deletion policy, no training use, actual files never leave the machine.
ADR-002
SQLite over vector database
Context: Previous attempt used Qdrant vector DB — separate server process, embedding pipelines, chunking strategy — all of which contributed to the project stalling.

Decision: SQLite with structured metadata cards. One row per document. Keyword matching for retrieval. Claude handles the full document in-context using its large context window — no chunking needed.

Tradeoff accepted: No semantic/fuzzy search across content. Acceptable at personal document scale (50–300 documents). Vector search can layer on top if the collection grows.
ADR-003
Flask over Streamlit or FastAPI+React
Context: Streamlit's execution model caused state management issues. FastAPI + React added a JavaScript build pipeline for a personal tool.

Decision: Flask with Jinja2. Single process, single port, one Python command. No build step. Server-side rendering with targeted JS for polling and search.

Tradeoff accepted: Full page reloads on form submit. Mitigated by background threading (ingestion is async) and JS-based live search and progress polling.
ADR-004
PyMuPDF for PDF parsing
Context: STEWARD must handle text PDFs, scanned PDFs, and mixed PDFs. The parser must detect type and route correctly without manual classification.

Decision: PyMuPDF for PDF parsing and PNG rendering. Detection rule: <50 characters per page = classified as scanned. Scanned pages rendered at 100 DPI (first pass) or 150 DPI (re-ingest). Cap at 8 pages per API call.

Tradeoff accepted: AGPL licence — acceptable for personal use. Higher token cost for image-based extraction vs text; mitigated by using Haiku for text, Sonnet for images.
ADR-005
Two-model extraction: Haiku for text, Sonnet for vision
Context: Initial build used Haiku for all extraction including scanned PDFs. Vision quality on Haiku for low-contrast scanned documents (legal deeds, receipts) was poor — dates missed, names hallucinated.

Decision: Route by doc type. Text PDFs → Haiku (4× cheaper). Scanned/mixed PDFs → Sonnet (significantly better OCR reasoning). Re-ingests always use Sonnet regardless of type, since the user has explicitly asked for higher quality.

Tradeoff accepted: Higher per-document cost for scanned docs. Justified by dramatically better extraction quality on exactly the docs that matter most — legal papers, property documents, scanned receipts.
